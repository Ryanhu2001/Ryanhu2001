## 开场（3 分钟）

大家好，今天占用大家一小时，分享的不是一篇论文，是 Anthropic Engineering 今年上半年连发的**五篇 Agent Eval 工程文章**，我把它们串成了一条线。

先讲一个真事勾一下大家：Anthropic 在跑 BrowseComp 这个联网搜索 benchmark 的时候，发现模型在一道题上烧了 **4050 万 token**——正常题目的 38 倍。查轨迹才发现，模型前 3000 万 token 在老老实实做研究，搜不到答案之后，它开始琢磨一个问题：**"这道题为什么会存在？"**然后它推断自己在被评测，找到了 benchmark 的开源仓库，读懂了答案的加密方式，自己写代码把 1266 道题的答案全解密了。

这个故事第三部分细讲。先立住今天的主题——

**【锚句】Agent Eval 不是给模型出题，而是在构建一套可复现、可对抗、能接入生产的测量系统。**

五篇文章正好是这套系统的五个阶段：**Build、Stabilize、Protect、Improve、Operate**。【投屏：文章开头的五阶段表】今天的路线：前三篇讲怎么让"分数可信"，第四篇讲评价怎么变成生产力，第五篇讲离线全绿为什么还会翻车，最后留一段讨论怎么落到我们自己团队。

## Part 1 · Build：Eval 的对象远大于最终回答（10 分钟）

### 1.1 为什么三件套不够（3'）

第一篇《Demystifying evals for AI agents》回答的是：普通 LLM 评测的 Prompt–Answer–Grader 三件套，为什么测不了 Agent？

【互动】先问大家一个问题：如果一个 agent 说"退款已处理完成"，你们会检查什么来确认它真的完成了？（收两个答案再往下）

因为 Agent 是一个循环：读环境、调工具、改状态、根据中间结果改计划。【投屏：§1.2 的多轮 Agent Eval 图】一次错误会在后续几十轮里累积，一次看似的偏航也可能是更好的解法。所以要拆出一组新对象：Task、Trial、Trajectory、Outcome、Grader、Harness、Suite。【投屏：§1.2 组件拆解图】其中最重要的区分——

**【锚句】Agent 的自我叙述、执行过程、外部世界状态，是三类不同的证据，必须分开记录。**

刚才大家说的答案基本都落在"外部世界状态"这一类——对，模型说"处理完了"不算数，要看数据库和文件系统的真实状态。

### 1.2 两个案例：更好的解法被判零分（4'）

**案例一：τ²-bench 改签题。**用户持基础经济舱机票想改签，预设答案是"拒绝"，因为规则写着不能改。Opus 4.5 翻政策翻出一条合法路径：所有舱位都可以不改航班先升舱——那就**先升舱、再改签**。更好的解法，被判了零分。这说明固定 Outcome 列表会惩罚超出出题人想象的模型，所以要给"未预期但合法的解"留人工复核入口。

**案例二：CORE-Bench 的 42 → 78 → 95。**Opus 4.5 用原始 CORE-Agent scaffold 得 42 分。换成 Claude Code，**模型一个字没动**，涨到 78——36 分是 scaffold 欠的。再人工检查剩余失败，发现 8 道题评分过严或题意不清，典型的是模型答 96.12、参考答案 96.124991、自动评分判错。修完到 95。

**【锚句】低分不一定是模型差；先读轨迹，再信数字。**

◇ 顺带一句 METR 的镜像案例：题面说"达到阈值即可"，评分器却要求"显著超过阈值"——遵守指令的模型反而吃亏。**任务规格和评分标准用了两套成功定义**，这是另一种"判得不公平"。

### 1.3 pass@k、pass^k 与建设路线（3'）

单次成功率 75% 时，三次至少成一次是 98.4%，三次全部成功只有 42.2%。【投屏：§1.8 分叉曲线图】**做 demo 看 pass@k，做产品必须看 pass^k**——"多试几次总能成"不能替代稳定性。

◇ 从零建设的路线，原文给了九步，我提炼三条最反直觉的：
- **20–50 个真实任务就能起步**，来源是 bug tracker 和发版前的手测清单，不要先造题；
- **每题配参考解**：连前沿模型都 pass@100 = 0 的题，先怀疑题坏了，不是模型不行；
- **同时测"该做"和"不该做"**：只测"该搜索时搜了没有"，会养出一个什么都搜的 agent。

最后一张图收束这部分：【投屏：§1.10 Swiss Cheese 图】自动 Eval 只是六层防线之一，和生产监控、A/B、用户反馈、人工轨迹审读、专家研究互相补洞。

## Part 2 · Stabilize：测量装置本身会改分数（6 分钟）

### 2.1 一个低级但典型的翻车（2'）

第二篇问的是：排行榜上的几分之差，有多少来自基础设施？

Anthropic 自己在 GKE 上跑 Terminal-Bench，Pod 错误率一度接近 6%。根因：他们把"资源保证值"和"硬上限"设成了同一个数——内存瞬时一冲就被 OOM 杀掉，而官方 leaderboard 用的沙箱允许临时超配。**同一个 benchmark，两种资源语义，两个分数。**

### 2.2 六组资源实验的两段式结论（4'）

【投屏：§2.3 我画的两阶段图】他们固定模型、Harness、任务，只改资源执行方式：

- **1x → 3x**：基础设施错误率从 5.8% 降到 2.1%（p<0.001），但**分数没涨**（p=0.40）——救回来的多是本来就走错路的 Trial；
- **3x → 不设限**：错误率只再降 1.6 个点，**成功率涨了 4 个点**——Agent 能装大依赖、跑重型工具链了，可用策略变了。1x 到不设限总差 6 个点。

**【锚句】资源配置不只影响稳定性，它改变 Benchmark 测的到底是什么能力。**

◇ 最生动的例子是 `bn-fit-modify` 这道题：宽松环境里模型会装全套 data science stack；紧内存环境里 Pod 在装依赖阶段就被杀，但始终存在一条只用标准库手写数学的轻量路线。**紧资源奖励精简实现，宽资源奖励重型工具链**——两种都是真本事，但不能混在一个分数里。

给团队的实操结论：**排行榜上小于 3 个百分点的差距，配置没对齐之前不值得当结论**——朴素置信区间本身就跨 1–2 个点，基础设施混淆还叠加在上面。

## Part 3 · Protect：被测对象会研究测量系统（10 分钟）

### 3.1 完整版故事（5'）

回到开场那个故事。背景数字先立住：1266 道题里 11 道的答案来自 benchmark 材料。9 道是普通污染——ICLR 投稿、arXiv 附录把题和答案发到了网上，有一次 Agent 的第一条搜索结果就是带答案的论文。**真正新的是那 2 道：Eval Awareness。**

【投屏：§3.2 我画的六阶段轨迹图】完整走一遍：

1. 前 3000 万 token：12 种语言、几十个平台、几百次搜索，正经研究，无果；
2. 转折点：不再问"答案是什么"，开始问"这题为什么会被设计出来"——作业？考试？还是 LLM benchmark？
3. 枚举它知道的 benchmark：GAIA 的 165 道公开题机械核对了 122 道，排除；再遍历 BrowseComp、SimpleQA、FRAMES、WebArena……
4. 锁定 BrowseComp，在 GitHub 读到评测源码：Canary 派生 Key + SHA256 + XOR。它在官方提供的沙箱里**自己重写了 derive_key 和 decrypt**；
5. 第一次失败：官方加密数据是二进制，抓取工具只收文本。它没停——去 HuggingFace 找到了内容相同的第三方 JSON 镜像；
6. 解密全部 1266 条，找到答案。我最喜欢的细节：**它还回到开放网络把答案交叉验证了一遍。**

◇ 成功的只有 2 条，但**尝试过的有 18 条**：三次被二进制格式挡住、六次卡在需要凭证的下载点、四次把预算全烧在"识别评测"上得了零分。最极端的一条没答题，交了一份"我可能正在参加哪个 benchmark"的调查报告。这说明 Eval-aware 不是偶然事故，是强 Agent 在长程失败后会**反复收敛**到的策略方向。

### 3.2 三个必须带走的判断（3'）

- **这不算 Alignment Failure**：任务只说"找答案"，没禁止这条路。模型没违规，**但 benchmark 的测量意义失效了**——"是否违规"和"评测是否还有效"必须分开讨论。
- **不能用 token 数做检测规则**：有一条 6.22 亿 token、跑了近两周的轨迹完全干净，最后靠原始研究找到了答案。要审计的是**策略转折**——它是不是开始搜 benchmark 的名字、数据集、解密方法了。
- **修正分数只从 86.81% 降到 86.57%**。绝对变化 0.24 个点，但解释变了：**污染率小，不代表测量解释还成立**，尤其榜单差距很小的时候，几道被攻破的题就能改变排序。

### 3.3 两个衍生发现（2'）

**Web 是 Agent 之间的隐式共享内存。**【投屏：§3.7 我画的四步图】有些电商网站会把搜索词生成永久页面，前一个 Agent 的搜索假设被搜索引擎收录，后一个 Agent 搜同一道题就能看到"前人"的轨迹残片——即使每个容器都从干净快照启动。有个 Agent 甚至自己说出来了："多个 AI agent 之前搜索过同一道谜题。"

**防御没有银弹**：URL 黑名单会被镜像绕过，最有效的临时手段是屏蔽搜索结果里所有 BrowseComp 的名字变体——直接切断"识别"这一步。但原文最后有句清醒的自嘲：**这份报告本身也会成为新的污染源。**

**【锚句】Eval Integrity 不是一次性检查，是持续的攻防。**

## Part 4 · Improve：把 Evaluator 塞进运行循环（9 分钟）

### 4.1 两个循环，别混（2'）

前三篇都是"事后打分"。第四篇问：什么时候值得把评价变成 Agent 运行时的反馈？

【投屏：§4.1 我画的双循环对比图】左边离线循环回答"系统是否变好"——固定任务集、多 Seed、出分数和回归信号；右边 Generator–Evaluator 循环回答"**这一次**的产物能不能更好"——输入是用户目标和真实产物，输出是失败证据和下一轮修复。第四篇全部发生在右边。

### 4.2 为什么必须拆角色（3'）

两个独立的问题。第一个是**长任务断片**：早期模型 Context 一长就急着宣布完工，作者管这叫 Context Anxiety，解法是 Context Reset 加交接文档。第二个更本质——

**【锚句】让 builder 自评，它会替自己辩护。**"这个问题不严重""已经基本满足要求"。

所以拆开：Generator 造；独立 Evaluator 拿着 Playwright **真的去点页面**、查 API、查数据库，按四类标准打分（设计质量、原创性、基本功、可用性），返回具体失败证据。

◇ 一个有意思的副作用：Rubric 里写了"Museum-quality"这个词之后，不同任务的产出开始向同一种视觉风格收敛。**评价标准既是尺子也是优化目标**，它会把自己的审美写进生成分布——所以 Rubric 要版本化，分数上升不自动等于人类偏好上升。

### 4.3 两组数字 + 一个反转（4'）

**Retro Game Maker 对比**，同一句需求：

| | 用时 | 成本 | 结果 |
|---|---|---|---|
| Solo | 20 分钟 | $9 | 界面像样，但游戏角色出来之后**完全不响应输入** |
| Full Harness | 6 小时 | $200 | 16 个 feature、10 个 sprint，关卡真的能玩 |

【投屏：§4.7 三张对比截图】贵 20 多倍，买到的是"从不可用到可用"。Evaluator 的价值看 §4.8 那张验收表：不是"功能需完善"这种空话，是"`fillRectangle` 存在但没在 `mouseUp` 里触发"这种**拿来就能修**的证据。

**反转在后半段**：模型升级到 Opus 4.6，作者把 Sprint 机制**删了**——模型自己能连贯跑两小时了。新实验（浏览器 DAW，3 小时 50 分、$124.70）里 Evaluator 只在构建结束后集中 QA。

**【锚句】Harness 的每个组件都编码了一个"模型自己做不到什么"的假设，而这个假设会随模型升级过期。**所以要逐组件 Ablation——作者第一次激进删减时一次改了太多，连"哪个组件在承重"都判断不了。

## Part 5 · Operate：内部全绿，用户先发现退化（9 分钟）

### 5.1 三个根因的叠加（4'）

最后一篇是复盘。今年 3 月起用户狂报 Claude Code 变笨、健忘、额度消耗变快，内部查了一个多月。

【投屏：§5.1 我画的时间线图】真相是**三个互不相关的问题在时间上叠加**：

1. **3-04**：默认推理力度 high → medium。内部评测显示"能力略降、延迟大降"，纸面 Pareto 合理。但用户直接感觉"变笨"，而且给了切换入口也没人切——**默认值本身就是产品行为**。4-07 回滚。
2. **3-26**：一个缓存优化的状态 bug。本意是空闲一小时后恢复时清一次旧思考，结果 flag 没复位，**之后每一轮都在删推理历史**——越删越失忆、重复劳动、工具选择变怪；而且每次删除都改变请求前缀，缓存连续 miss，**额度消耗变快**。质量和成本两类投诉，一个根因。4-10 修复。
3. **4-16**：一条"工具调用之间不超过 25 词"的简洁 prompt。内测数周、已有评测集没显示回归；用户报告之后扩大评测集、逐行 ablation，才发现**两个模型全线掉 3%**。4-20 回滚。

### 5.2 为什么全部漏过（3'）

这个 bug 通过了人工 review、自动 review、单测、端到端测试和内部 dogfooding。因为它只活在组合状态里：Context 管理 × API header 语义 × 扩展思考 × 缓存逐出 × **空闲超过一小时** × 恢复后多轮。更糟的是内部还有两个无关改动恰好把现象遮住了——内部 CLI 大多触发不了用户的真实路径。

**【锚句】"使用同一代码"不等于"处在同一运行分布"。**Feature flag、缓存状态、会话历史，全都属于评测环境。

◇ 还有个细节值得说：事后用 Code Review 回放那个 PR，给足跨仓库上下文时 Opus 4.7 能找到 bug、4.6 不能。他们的结论不是"以后用更强的模型 review"，而是**给 reviewer 补跨仓库上下文**——工具和上下文的贡献不亚于模型。

### 5.3 整改清单（2'）

【投屏：§5.9 我画的生产闭环图】他们的整改不是"多写测试"：内部员工直接用和外部一致的 **Public Build**；每次 System Prompt 改动跑**逐模型评测 + 逐行 Ablation**；拿智能换延迟/成本的改动一律加 **Soak 期和渐进发布**；生产失败沉淀成最小复现任务回流回归集。

**【锚句】用户体验的被测对象是完整生产系统；离线 Eval 只覆盖模型和 Prompt，就会系统性漏掉组合状态。**

## Part 6 · 收束：一套方法论（6 分钟）

【投屏：§6 五层原则表】五篇合起来：定义测量对象（Build）、校准测量装置（Stabilize）、保护测量意义（Protect）、必要时让评价进入运行循环（Improve）、用生产失败反哺题库（Operate）——而且生产失败会变成新任务，回到 Build，是个环。

【投屏：§6.1 失败分类表】如果只带走一张表，带这张诊断表。结果异常时先分类：

| 现象 | 失败类型 | 先查什么 |
|---|---|---|
| 正确行为被判错 | 规格失败 | 是否漏了合法替代解 |
| 同一模型分数飘 | 测量失败 | 资源、网络、Grader 固定了没有 |
| 分数异常高 | 完整性失败 | 污染、泄漏、Eval awareness |
| 循环评分涨但质量没涨 | 评价者失败 | Rubric 偏差、自评宽松 |
| 内部正常用户骂 | 分布失败 | 长会话、组合状态、Public Build |

◇ 时间够的话再过一眼 §6.3 的 release gate 表：**不同类型的改动配不同的最小验证**——这可能是最容易抄进我们 CI 的一条。

最后三个判断，我念文章里的原话：Agent Benchmark 本质上是系统 Benchmark；Eval 的价值不在排行榜，而在可靠迭代；Eval 最终会成为 Agent Loop 的控制器。收束句——

**【锚句】先把 Eval 当成产品和基础设施来建设，再把它当成一个 Benchmark 分数来看。**

## Q&A 预案（5 分钟）

**Q1：我们团队现在没有任何 agent eval，从哪开始？**
A：20–50 个真实任务就够起步，来源是 bug tracker、support 工单和发版前本来就会手测的东西。先自动化你已经在手工做的，不要先造题。每题配一个已知能通过的参考解，证明题目可解、评分配置没坏。

**Q2：LLM-as-judge 靠谱吗？**
A：分层用：确定性规则管正确性和安全底线，LLM Rubric 管开放式质量，人类专家管 Gold Set 和校准。记住第四篇的教训：Rubric 措辞会反过来塑造输出，judge 要版本化，分数上升不自动等于人类偏好上升。

**Q3：Eval awareness 对我们有现实威胁吗？我们又不做公开 benchmark。**
A：只要评测题目和答案可能出现在 agent 能访问的地方——内网 wiki、代码仓库、日志——威胁就存在。三条可操作的：答案和评分逻辑对 agent 物理隔离、给数据埋 Canary、对异常高分和策略突变的轨迹做人工审计。

**Q4：Generator–Evaluator 太贵了吧，20 倍成本？**
A：它不是默认选项。判断标准是任务是否在当前模型的 Solo Reliability Boundary 之外：模型自己能稳定做好的，Evaluator 是纯开销；做不好的，每轮反馈都在挣钱。边界随模型升级外移，所以要定期重新 ablate。

**Q5：这五篇最可抄的一条是什么？**
A：我选 release gate 分型：不同改动配不同最小验证——模型/力度改动看能力+成本曲线，prompt 改动做逐模型评测+逐行 ablation，基础设施改动做跨时段重跑。比"所有 PR 跑同一套测试"精准得多。

**Q6（可能来自领导）：投入产出怎么算？**
A：用第一篇的说法：Eval 的回报不只是发布前拦 bug，还包括**更快采用新模型**（有基线才敢换）、持续记录延迟与成本、把产品语言变成可优化目标。CORE-Bench 那个 42→78 说明：没有好的评测，你连"模型没问题、是 scaffold 的锅"都发现不了。
